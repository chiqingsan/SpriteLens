# 技术评估与路线规划（2026-10-09）

> 历史文档：本报告写于项目仍名为 RocoPeek 时期，文中的「本项目/我们」
> 即现在的 SpriteLens；结论与实测数据保留原样，仅项目名已随迁移更新。

> 回答两个问题：① 用 Web UI 承接数据是否最优？② Python 做流量分析是否有性能问题？
> 方法：在本机对现有管线做实测基准（Python 3.14.6，登录突发 561 帧 / 110KB 真实规模合成数据），
> 不做猜测。

---

## 0. 结论速览

1. **性能不是问题，且余量极大**。全管线（切帧+AES 解密+拆分+schema 解码）实测
   **约 4,200 帧/秒 / 3.2 万条小消息每秒**；登录突发 110KB 全量处理 **约 42ms**（不挂事件日志时）。
   游戏实际负载是 5~50 条消息/秒，**余量 600 倍以上**。
2. **真正的瓶颈不在 Python，而在"持久化 + UI 刷新"这两处增量**：
   实测出两个真实热点（见 §3），都是可以低成本修掉的工程问题，与语言无关。
3. **Web 承接数据是正确方向，但不该推翻 PyQt**。推荐
   **"PyQt 壳 + 内嵌 FastAPI（同时提供 REST/SSE 与本地页面）"** 的渐进路线，理由见 §4。
4. 当前最大痛点不是性能，而是**产品成熟度**：无持久化、无静态数据、无 API 生态
   （详见 `docs/COMPETITOR_ANALYSIS.md` §3 与本文 §5）。

## 1. 实测数据汇总

### 1.1 管线单点成本

| 项目 | 吞吐 | 单条成本 |
|---|---|---|
| AES-128-CBC 解密（pycryptodome） | 133,783 帧/s（17.4 MB/s） | 7.5 µs |
| wire 解码（97B protobuf） | 110,978 帧/s | 9.0 µs |
| 切帧 + 解密 + 拆分（整块 feed） | 88,374 帧/s | 11.3 µs |
| **全管线 + schema 解码** | **42,002 帧/s（6.8 MB/s）** | **23.8 µs** |
| 持续小消息（0x2001 类操作帧） | 32,734 条/s | 30.5 µs |

### 1.2 登录突发（561 帧 / 110KB，实测）

| 场景 | 耗时 | 说明 |
|---|---|---|
| 无事件日志 | **41.9 ms** | 管线真实成本 |
| 挂事件日志（现状） | 55.6 ms | 日志净增 13.7 ms |
| UI 轮询最大等待 | 57.2 ms | 仅 1 次 >20ms（突发瞬间） |
| UI 轮询中位等待 | 0.02 ms | 平时无感 |

### 1.3 启动与内存

| 项目 | 实测 |
|---|---|
| schema 库加载（3458 消息定义） | 113.5 ms |
| opcode 目录加载 | 3.9 ms |
| schema 常驻内存 | 4.6 MB |

### 1.4 UI 与数据侧成本

| 项目 | 107 行 | 1000 行 | 5000 行 |
|---|---|---|---|
| QTableWidget 逐格重建（现状） | 3.5 ms | 38.0 ms | — |

即使宠物涨到 1000 只（38ms）也仍在可接受范围。Web 方案的 JSON 开销更低（107 行 0.8ms）。

## 2. Python 的性能边界在哪

按实测数据推算（单核）：

| 负载 | 每秒消息数 | 管线占用 | 结论 |
|---|---|---|---|
| 游戏常态操作 | 5~50 | 0.15%~1.5% | 无感 |
| PVE 战斗高峰 | ~200 | 6% | 无感 |
| 登录/进场景突发 | 数百帧/秒级 | 峰值几十 ms | 可接受 |
| **理论上限** | **~32,000** | 100% | 游戏永远达不到 |

**关键判断**：只有当消息率超过 **每秒 3 万条** 时 Python 才会成为瓶颈——
这比游戏实际负载高 3 个数量级。**"Python 做流量分析有性能问题"这个担心，在本题上不成立。**

真正需要注意的两个细节：

1. **scapy 的解析成本不在我们控制内**：BPF 已在内核态过滤（`tcp port 8195`），
   只有命中端口的包才进 scapy。我们已用"嗅探线程只做分类+重组、重活交给队列"的
   两段式设计规避了回调堆积——这是正确的架构，比竞品（在回调里做更多）更稳。
2. **锁粒度**：`MonitorService._handle_chunk` 持有 `self._lock` 走完
   "解密+解码+回调"全程（见 §3.1）。突发 100KB 时占锁 ~56ms，
   UI 轮询会等一下（实测 1 次 57ms）。功能上无碍，但值得优化。

## 3. 实测出的真实热点（低成本可修）

### 3.1 事件日志在监听锁内做 json.dumps + 每条 flush

**证据**：`services/monitor_service.py` 的 `_emit()` 在**持锁**状态下
逐条调用 listener；`services/event_logger.py:handle_packet()` 每条事件都做
`json.dumps(完整 decoded 树)` + `file.flush()`。

实测：561 帧突发下净增 **13.7ms**（含 dumps 73µs/条 + flush 19.5µs/条），
且这段时间 UI 的 `drain_events()` 被阻塞（实测最长 57ms 等待）。

**为什么现在不痛**：57ms 的一次等待在登录时表现为"界面顿一下"，可接受。
**为什么将来会痛**：消息率上去（战斗+多业务同时开）时，锁内 IO 会放大成持续卡顿。

**修法**（按性价比）：
1. 日志写入移到独立线程（有界队列 + 批量 flush）；
2. 或最低成本：`_emit()` 中把 listener 调用放到锁外（事件已 append，锁内只做必要计数）。

### 3.2 UI 全量重建表格

**证据**：`ui/pages/pet_page.py:_rebuild_pet_table()` 每次变更 `setRowCount` +
逐格 `setItem` 重建整表；1000 行实测 38ms。

**现状可接受**（107 行 3.5ms），但宠物上限涨到千级或加多列后需要换
`QTableView + QAbstractTableModel`（仅刷新脏行）。

### 3.3 recorder 每条 chunk 也 flush

**证据**：`recording/recorder.py:append()` 每条 chunk 后 `file.flush()`。
录制是旁路，**且用户显式开启才写**，暂时不修——但若开启录制后遇到丢帧,
这里是第一嫌疑。

## 4. "Web 承接数据"评估

### 4.1 竞品为什么全选 Web

| 竞品 | UI 形态 | 原因 |
|---|---|---|
| roco_helper | 本地 Web（4939） | 筛选器矩阵/滑块/分页表格 = Web 生态强项 |
| rocom-capture | Go + Web | 同上 + 天然可远程 |
| innovationb1ue | FastAPI + React | 战斗面板需要高频状态更新 |
| RKMS | Web 控制台 | 需要过滤器 DSL 等复杂交互 |

**Web 的三个不可替代优势**：
1. **UI 组件生态**：20+ 维筛选器、双端滑块、数据矩阵、虚拟滚动表格——
   用 Web 是"安装一个库"，用 Qt 是"每种自己写"。
2. **多端访问**：手机/平板/另一台电脑都能看（抓包机放一边，人拿手机看数据）。
3. **天然 API**：页面消费的就是 API，第三方（如 roco-catcher）可直接复用——
   这是 roco_helper 形成生态的根本原因。

### 4.2 但不该推翻 PyQt 重写

| 维度 | 纯 PyQt（现状） | 纯 Web（推倒重来） | **PyQt 壳 + 内嵌 Web** |
|---|---|---|---|
| 工程量 | 0 | 全部 UI 重写（最大成本） | 增量：加一个 HTTP 服务 + 逐页迁移 |
| 实时性能 | 直接调用，最优 | 需 WS/SSE + JSON | 同纯 Web |
| 单进程/离线 | ✅ 无端口暴露 | ❌ 需管理端口 | ⚠ 端口仅绑 127.0.0.1 |
| 多端访问 | ❌ | ✅ | ✅ |
| 与抓包协同 | 同进程，零拷贝 | 同进程 | 同进程 |
| API 生态 | ❌ | ✅ | ✅ |
| 复杂筛选用组件 | 手写成本高 | ✅ 生态现成 | ✅ 逐步迁移 |

**推荐路线**：**PyQt 保留为"壳 + 系统页"，数据页逐页迁移到内嵌 Web。**

具体形态：
```
┌─ PyQt 主进程 ───────────────────────────────┐
│  监听控制页（网卡/密钥/状态）  ← 保留 PyQt   │
│  系统/诊断页                  ← 保留 PyQt   │
│  ┌─ FastAPI（127.0.0.1:随机端口，仅本机）─┐  │
│  │  GET /api/pets     获取宠物快照        │  │
│  │  GET /api/events   SSE 实时事件        │  │
│  │  GET /            内嵌数据页（Web UI）  │  │
│  └──────────────────────────────────────┘  │
│  pywebview 承载页面（系统 WebView2，额外体积 ≈ 0）│
└─────────────────────────────────────────────┘
```

> ⚠️ **承载形态修正（2026-10-10）**：上图原写"QWebEngineView 嵌内嵌页面"——**不要采用**。
> `PyQt6-WebEngine-Qt6` 自带完整 Chromium，wheel 实测 **132.4 MB**（量级向 Electron 靠拢），
> 会让"零重写、体积不变"的前提失效。正确形态是 **pywebview + 系统 WebView2**（本机已装，额外体积 ≈ 0）。
> 详见 `docs/ARCHITECTURE_DECISION.md` §3。

**分阶段**：
- **阶段 1**（低风险）：只加 FastAPI 后端 + API，不开页面。验证 API 契约与持久化。
- **阶段 2**：宠物仓库迁到 Web 页（先做筛选器/矩阵这些 PyQt 难写的）。
- **阶段 3**：战斗面板/战报（最高频更新、最需要 Web 组件）。
- **PyQt 保留**：监听控制、事件流专家视图、诊断——这些是低频交互，PyQt 更省事。

**为什么不是"完全弃 Qt 用浏览器"**：桌面工具的核心价值是"双击即用、无浏览器、
无端口管理"。保留 PyQt 壳让首次体验不变，同时把复杂 UI 外包给 Web 生态。

## 5. 项目成熟度痛点评估（非性能）

按"影响用户价值"排序：

| # | 痛点 | 现状 | 影响 | 修法 |
|---|---|---|---|---|
| **P0-1** | **无持久化** | 宠物快照仅内存，重启即失 | 每次开游戏都要重抓；无法积累历史 | SQLite（参考 roco_helper `{domain}_{uid}` 但改统一 schema+uid 列） |
| **P0-2** | **无静态数据** | wire 层只有 `field_N`，没有名字/技能/图鉴 | 筛选器/矩阵/战斗分析全都无法显示人话 | 引社区 JSON（innovationb1ue 的 `data/game/*.json`） |
| **P0-3** | **宠物字段浪费** | `attribute_info`/`skill` 等已在 wire 层拿到但未提取 | 六维、技能组这些"最有价值的信息"看不到 | 扩展 `domain/pets.py` 的提取字段 + UI 列 |
| **P1-1** | **无 API** | 数据只能自己看 | 无第三方生态，无法多端 | 随 §4 阶段 1 一起做 |
| **P1-2** | **无事件域验证** | 战斗/背包/任务 帧未实测 | 规划中的 15 个业务域无法开工 | 一次完整业务录制（登录→开面板→PVE→PVP） |
| **P2-1** | **锁内 IO** | 见 §3.1 | 高负载下卡顿 | 异步日志 |
| **P2-2** | **表格全量重建** | 见 §3.2 | 千级行时浪费 | QAbstractTableModel |

## 6. 建议路线（三个月视角）

### 第一优先：把"数据资产"做实（1~2 周）

```
1. SQLite 持久化层
   - 表：pets(uid, gid, conf_id, raw_json, updated_at)、events、sessions
   - 迁移：PetRepository 后端从 deque 换成 SQLite，VM 接口不变
   - 收益：重启不丢、可查历史、捕捉/对战统计有地基

2. 静态数据导入
   - tools/import_gamedata.py：拉 innovationb1ue 的 data/game/*.json
     （pet_species/skill_map/type_chart/nature_map，约 12MB）
   - 映射：conf_id → 名字/系别/蛋组/稀有度；技能 id → 名字/威力/能耗
   - 收益：立刻能显示"魔力猫 草 动物组"而不是"2000671"

3. 宠物页升级
   - 全字段展示（六维/性格名/系别/蛋组/体重/身高）+ 多列排序
   - 收益：对标 roco_helper 主界面，功能上不再是"半成品"
```

### 第二优先：API 与 Web 化起步（2~3 周）

```
4. FastAPI 后端（127.0.0.1）
   - GET /api/pets、GET /api/events (SSE)、GET /api/status
   - 收益：多端访问 + 第三方生态 + 为 Web UI 铺路

5. 宠物页 Web 化（第一个迁移页）
   - 左筛选器（20+ 维、OR/AND、双端滑块）+ 右表格
   - 顺带把"孵蛋覆盖矩阵"做出来（差异化亮点）
```

### 第三优先：事件域与差异化（2~3 周）

```
6. 完整业务录制 → 验证战斗/背包/任务帧
7. 对战观测（M4）/捕获中心（M6）：实时回合流 + 捕获概率
8. 战报复盘（M5）：PVP 伤害统计
```

### 持续：工程卫生

- 锁外日志（§3.1）、QAbstractTableModel（§3.2）
- 架构测试（仿 innovationb1ue 的 `test_architecture.py`）

## 7. 一句话总结

**性能担忧可以放下**：实测管线有 600 倍以上余量，Python 在本题上完全够用，
真正的两个热点（锁内日志 IO、表格全量重建）都是小修。

**Web 方向正确但不必重写**：推荐 "PyQt 壳 + 内嵌 FastAPI" 渐进路线——
监听控制留 PyQt（低频、简单），数据页逐步迁 Web（高频、复杂、需要生态）。

**当前最该做的不是性能优化，而是补三个短板**：持久化、静态数据、对外 API。
这三件事做完，项目才从"能跑通的 MVP"变成"能积累价值的产品"。
