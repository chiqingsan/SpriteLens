## 1. 基线、结论与限制

- 审查时 HEAD：`de6f1c0eb12690ad8df62df209559edf78ae257b`，工作区存在大量未提交修改及未跟踪文件；结论针对当时工作区，不能仅 checkout 此提交复现。
- 用户明确主要问题是内存占用偏高。本轮未修改业务代码、未启停当前抓包、未关闭主窗或雷达、未操作游戏。
- 已检查正在运行的 SpriteLens 进程及其 WebView2 子进程，排除机器上其他应用的 WebView2；另在独立 Python 进程中回放本地录制。
- 最明确的可优化项是桌面链路无人消费的完整事件历史。页面驻留与 WebView2 的成本需要进一步分摊，不能据此宣称已经定位全部内存。
- 没有当前 WebView2 的堆快照，没有长时间泄漏曲线；短时 CPU 采样不能证明所有场景正常。
- 运行实例启动早于最新前端构建，进程采样与最新前端源码不是严格同一版本；前端改造前必须用同一构建重新建立基线。
- 不承诺固定节省多少进程内存。Python 跟踪堆、私有工作集、私有提交和 GPU 内存是不同指标，释放 Python 对象也不保证工作集立即等量下降。

## 3. 测量证据

### 3.1 当前实例进程采样

Windows 私有工作集聚合结果（MiB，四舍五入）：

| 部分 | 私有工作集 |
| --- | ---: |
| Python 后端及宿主运行时 | 264 |
| 两个 WebView2 renderer | 268 |
| WebView2 GPU 进程 | 53 |
| 浏览器、网络等辅助进程及启动器 | 96 |
| 总计 | 681 |

私有提交合计约 892 MiB。普通工作集直接相加约 1.8 GiB，但包含重复计算的共享映射，不能全部视为独占内存；私有工作集也不覆盖全部共享/GPU 成本。两个 renderer 未通过调试协议逐一映射到页面，不将其中任一个的全部占用直接归因为某个 Vue 组件。

12 秒 CPU 采样未见满载。该结果不覆盖登录突发、切场景及长期运行。当前本地库约 10.7 MiB、1 个账号、1,400 只宠物；这是规模背景，不是通用数据上限。

### 3.2 完整事件历史的隔离对照

方法：在独立进程里流式读取已有录制，用真实 schema、静态目录与 `MonitorService.on_chunk` 解码；密钥只读加载，不输出；检查点写入用内存替身，不写真实配置、密钥、数据库或日志。不注册业务仓库及事件日志监听器，因此这不是完整应用的内存测试。

`tracemalloc` 在模块导入之后、加载 schema/目录之前开启。对照只在实验实例中将事件 deque 替换为 `maxlen=0`，不修改项目或在线实例。生产实现不得照抄这种私有字段替换。

| 相同录制前 5,000 段 | 默认保留 2,000 条事件 | 实验中不保留事件 |
| --- | ---: | ---: |
| 当前跟踪分配 | 76.08 MiB | 14.95 MiB |
| 跟踪分配峰值 | 215.96 MiB | 36.63 MiB |

默认组继续完整回放：33,263 段、39,173 次成功解密、解密失败 0、缺密钥 0；结束时保留 2,000 条事件，当前跟踪分配 37.60 MiB，调用 `drain_events()` 并释放返回结果后为 15.04 MiB。

无历史组前 5,000 段成功解密 3,174 次、解密失败 0。所见最大单条载荷为 162,633 字节，展开为 53,430 个字段节点（opcode `0x0102`）。schema 加载后跟踪分配约 4.60 MiB，全部已测静态目录加载后合计约 14.44 MiB。

限制：前 5,000 段对照只证明历史保留的内存影响，尚未对两组做全部业务产出等价验证；完整组的约 80.6 秒包含分配跟踪开销，不作为正常回放吞吐指标。实验脚本未纳入项目，原始录制、会话密钥和身份不得纳入测试样本或提交。

## 4. 修复切片

优先级表示实施价值，不表示所有候选项均已证实为主要根因。编号、顺序与持续状态以 ROADMAP 为准；一次实施一个编号。

### PERF01：桌面模式不保留无人消费的完整事件历史

- 证据：`services/monitor_service.py` 中 `_events = deque(maxlen=2000)`，`_emit()` 无条件 append；生产代码调用 `drain_events()` 的位置只有 `recording/replay.py`。桌面功能通过已注册监听器消费同一事件。隔离对照见 3.2。
- 范围/状态所有者：MonitorService 拥有缓冲；组合根与 CLI 决定是否需要收集。核对其他调用方和现有回归后确定最小内部接口，不新增用户配置页或诊断框架。
- 修复方向：桌面链路不驻留完整事件历史；CLI/明确诊断调用方按需收集。监听器、统计与账号路由继续工作，不用 UI 定时 drain 来维持无意义的生产缓冲。
- 失败边界：回放仍能得到预期事件；监听器异常隔离、采集启停、连接恢复、多账号归属均保持。不得把“取消历史”实现为丢弃业务事件或关闭日志。
- 验收：复用 `tests/test_monitor_service.py`、`tests/test_recording.py`，按实际装配变更选择相关用例；验证事件顺序/内容与业务快照不变。使用同一输入比较跟踪堆及进程私有内存；大包突发后不再因桌面历史保留事件树。不要求精确复现本报告的绝对 MiB。

### PERF02：雷达消息只处理一次

- 证据：`web/static/radar.js` 的 `addEventListener('message', ...)` 在挂载后手动调用 `channel.onmessage`；`frontend/src/pages/FloatingRadar.vue` 又设置该事件属性处理器。二者同时注册，正常消息会进入组件两次。
- 范围/状态所有者：启动脚本拥有挂载前消息队列；组件拥有挂载后的消费。只调整交接，不改变 BroadcastChannel 契约或增加 WS。
- 修复方向：保留唯一的挂载后消费路径，挂载前排队消息仅交付一次；若移除临时 listener，必须覆盖挂载交接时序。
- 失败边界：慢加载、初始化失败、关闭/重开、挂载交接消息、断线/恢复订阅与心跳失效；不得因去重遗漏清空指令。
- 验收：一条 snapshot/summary 只调用一次对应处理；初始化期间排队顺序与数量正确。复用 `FloatingRadar.test.ts`，必要时在启动桥交接层补最小请求时序用例，组件测试本身不能证明原生启动脚本已修复。涉及 Vue 时构建；主窗口最小化后雷达仍更新。
- 边界提醒：现有 stale 分支保留旧实体的问题属于数据有效性约束；不得在本次性能修复中进一步固化该行为，也不得用失效快照填充雷达来掩盖开销。

### PERF03：测量并收敛离页驻留

- 证据：`web/static/app.js::switchPage` 对多数已访问页面只 pause；`app.css` 的 `page-cached` 对背包、蛋仓、附近页保留布局。Vue 实例、DOM 和页面数据可以在离页后继续驻留。机制明确，但当前没有每页 heap/DOM/图片占用的分摊证据。
- 范围/状态所有者：原生壳只管导航；桥接管挂载/释放；页面管筛选、选中、滚动和草稿。先测一个重页面，再做局部改造，不直接引入全局 store 或全壳重写。
- 修复方向：比较初次进入、离开、重复返回的 retained heap、DOM、私有工作集。对已证明重的页面保留轻量操作状态、按需释放重实例/数据，或采用有依据的有限驻留。不能简单一律卸载、取消缓存或把全部页面改成 `display:none`。
- 失败边界：离页请求取消、旧响应迟到、切号/切场景、未保存草稿、退出保存失败、恢复选中项已被删除；归属失效必须清空旧内容。
- 验收：重复至少 10 轮固定导航，记录是否平台化及相对基线收益；核对筛选、阅读位置、焦点、选中和草稿恢复。首次/主动/后台加载明确区分，不以闪动、回顶或失效缓存换内存。使用相关 composable 回归；涉及布局必须执行项目极限布局与连续更新验收，不能仅以构建通过宣告完成。

### PERF04：雷达独立入口与按需页面加载

- 证据：`frontend/src/main.ts` 静态导入/重导出各页面桥，当前产物一个主要 JS 包约 429 KiB、CSS 约 190 KiB；`radar.js` 也导入统一 `entry.js`。加载了代码不等于挂载所有组件，不能据包大小推算全部 renderer 内存。
- 范围/状态所有者：Vite 入口、桥接、`tools/frontend.py`、`web/frontend_assets.py` 的生成/发布契约。先核对现有 entry、manifest、源指纹和样式等待逻辑。
- 修复方向：优先让雷达只引用所需页面与共享组件；其他页面按真实收益再拆分动态导入，复用公共依赖，避免复制 Vue。无需提前统一路由或新增依赖。
- 失败边界：缺 chunk、源/产物不匹配、样式尚未就绪、初始化失败与重试、打包资源漏收；不能破坏静态资源发布所有权。
- 验收：检查实际请求图和产物依赖，证明雷达不再导入无关业务页；记录冷启动与内存变化。构建并发布至运行目录，按影响复用 `tests/test_frontend_contract.py` 与启动验证；真实 WebView2/EXE 未测时明确标注。收益不足时不要继续扩大拆分范围。

### PERF05：事件日志批次及积压内存有明确预算

- 证据：`services/event_logger.py` 的队列上限 8,192 条完整事件；worker 持续取到队列暂时为空才开始写入，batch 没有独立上限，持续生产时可超过队列容量。事件树大小差异很大，因此条数上限不是内存上限。未测得在线积压大小，不把它认定为当前全部内存来源。
- 范围/状态所有者：EventLogWriter 独占队列、批次和文件；组合根负责关闭。日志与 monitor 可共享事件对象，不将两处持有误算为两份深复制。
- 修复方向：先给每批明确上限，保证持续输入下也能写入并释放引用；再基于测量建立积压预算/过载策略。不能仅用 `payload_len` 冒充解码树字节数，也不能每包递归深算对象大小造成新的热路径瓶颈。不要把 JSON 序列化搬回抓包锁内。
- 失败边界：慢盘、持续生产、队列满、单个超大事件、写失败、分片切换、flush barrier、关闭 sentinel、关闭超时与重试。日志过载仍可丢诊断并累计计数，但不阻塞业务采集，不虚报 flush/关闭完成。
- 验收：复用 `tests/test_event_logger.py`，必要时补持续生产和关闭时序回归；慢写替身下记录队列+在写批次的峰值及丢弃计数，验证 barrier 前已受理事件的既有完成/失败语义。不能只测队列长度，也不能静默关闭默认诊断日志。

### PERF06：减少协议解码中的展示对象与中间树分配

- 证据：`protocol/wire.py` 先生成 WireField 树，`protocol/schema.py` 再递归生成含 no/name/type/value/raw/children/text 的字典树；`value` 通常是展示字符串，`raw` 又保留强类型原值。两类树在转换阶段重叠存活，节点数量见 3.2。
- 进入条件：PERF01 完成并重新测量后，确认剩余解码分配仍值得优化再实施；这是高风险协议契约变更，不与缓存删除捆绑。
- 范围/状态所有者：protocol 拥有解码表示，domain 拥有业务解释，事件日志拥有诊断序列化。先搜索所有字段消费者，保留未知字段与缺 schema 的业务兜底。
- 修复方向：优先评估按需生成展示字段或减少中间表示，按最小变更选择一种。不得未经消费者审计就删除 name/type/value，也不得为省内存把字段号/bytes/int 转成失真字符串或截断业务树。不能用未验证的 opcode 白名单跳过解码。
- 失败边界：缺 schema、未知 opcode、大嵌套包、损坏字段、非 UTF-8、64 位 ID、登录/背包/蛋仓/场景完整及增量数据；异常语义与账号身份不能变化。
- 验收：复用 `tests/test_wire.py`、`tests/test_schema.py` 及受影响领域回归；同一录制比较业务提取、未知字段及诊断可用性，分别记录无 tracing 的吞吐与有 tracing 的分配。协议产出不等价时撤回该切片，不能只凭性能数字通过。

### PERF07：状态摘要按版本复用，避免每拍全量构造

- 证据：`web/server.py::_push_loop` 每 0.5 秒构造并编码完整状态后才比较；无 WS 客户端时也会运行。`routes_capture.py::_state_payload` 创建 PetView，宠物仓库重新排序/复制快照并聚合统计，其他域也取快照。主要影响分配频率、CPU 与锁竞争，尚未测量收益。
- 范围/状态所有者：业务域维护自身版本与摘要；服务层维护推送/连接；场景仓库推进插值。不得通过跨层读取私有状态拼接不一致快照。
- 修复方向：以 uid、版本、账号代次等必要依赖复用稳定业务摘要，采集计数/安装进度等继续及时更新；评估无订阅者时减少纯展示构造。不能只按 pets_version 缓存整个 state，也不能为跳过构造而停止必要的场景推进。
- 失败边界：版本未变但身份/采集/环境改变、同版本切号、重连首帧、切场景、服务停止、无人订阅后重新连接；附近数据的失效必须及时传播。
- 验收：复用 `tests/test_web_server.py`、`tests/test_pet_snapshot_contract.py`、`tests/test_account_domain_contract.py` 的相关用例；测静止数据与持续变化时的构造次数/耗时。观察快慢请求、失败重试、推送、实体增删、窄窗与高 DPI，不出现工具栏闪动、内容清空重建或回顶。

## 5. 通用实施与验收流程

1. 开工先执行 `git status --short`，阅读 AI_CONTEXT、DEVELOPMENT_GUIDE、ARCHITECTURE 和所选编号；保留现有未提交工作。记录 HEAD、相关 diff、运行构建指纹及测量场景，不能假设本文仍完全对应当前源码。
2. 一次只领取一个编号。写明输入假设、状态所有者、改动范围、失败分支和验收方式；本报告列的是方向，不授权展开整个阶段或重写基础设施。
3. 固定同一数据、窗口尺寸/DPI、页面、雷达开关、录制/日志开关和运行时长，对比修改前后。不要为获得好看的数字同时关闭日志、减少数据或关闭雷达。
4. 后端隔离实验使用只读输入和临时/内存副作用替身；不能直接使用会写真实密钥目录的普通 CLI 回放作为无副作用基准。录制、密钥、UID 和本机路径不进入提交；可提交回归只用合成样本。
5. 分别记录：Python 跟踪分配当前值/峰值；进程树私有工作集/私有提交；同条件 CPU；必要时 renderer heap/DOM 与 GPU 指标。不开 tracing 的吞吐与开 tracing 的内存测量分开。工具只用于本次诊断，不建立统一性能门禁。
6. 至少覆盖冷启动、登录/大包突发、静止采集、页面往返、雷达开关与长时间运行；按切片选必要场景。记录采样时长和稳定阶段，短时单点不能证明不存在泄漏。若只覆盖隔离实验，标为“已实现，桌面验收待完成”。
7. 遵守禁止 Computer Use 的项目约束。使用命令、API、测试及 Playwright；无法取得真实 WebView2 调试数据时明确缺口，不把独立浏览器结果冒充在线实例证据。
8. 布局变更覆盖正常/极限数据、最长名称/多行、最多徽章、缺失/异常、空/加载/错误态、最小窗口/窄屏、高 DPI 与字体回退；做真实渲染目视检查。动态变更观察连续更新，保留有效同周期内容，但请求失败或归属失效后的无效附近数据必须留空。
9. 交付写明改动、相关验证、前后测量、未覆盖项与回退条件；只更新 ROADMAP 对应编号。保留草稿与关闭失败语义，不通过强制 GC、定期清空业务数据或强制裁剪工作集掩盖根因。

## 6. 暂不扩大范围及文档校正

- 静态目录约 14.44 MiB，不先做全量懒加载；SQLite 当前规模不足以支持换库。素材磁盘体积与解码驻留不能混同，也不能假设所有图片已加载。
- Npcap 当前缓冲为 32 MiB，TCP 重组已有 256 KiB 历史窗口和单方向 8 MiB pending 上限；不未经丢包/突发测试直接调小。
- `AccountSessions._accounts` 未见非活跃账号淘汰，可作为多账号长期运行的后续观察点；当前本地库仅一个账号，不把它列为本轮已确认主因，也不提前增加 LRU。
- 当前原始录制、KeyStore 和 SceneCheckpointStore 已是后台写入；ARCHITECTURE 中部分“同步 IO”描述需要在相关模块交付时按现状校正，不能照旧文档重复实现。异步不代表没有积压、峰值或停止预算风险。
- 本报告不批准保留失效的附近/雷达快照；优化仍受 AGENTS/UI_GUIDE 的有效性及无闪动要求约束。若需要修复独立的有效性缺陷，应单列范围与证据，不能混入性能数字掩盖。
