# 方向评估：Electron + Rust 重构是否值得

> 历史文档：本报告写于项目仍名为 RocoPeek 时期，文中的「本项目/我们」
> 即现在的 SpriteLens；结论与实测数据保留原样，仅项目名已随迁移更新。

> 命题：Rust 做协议底层，Electron 做应用 UI，替换当前 Python(PyQt6) 单体。
> 方法：基于本机实测数据与前序性能结论（`docs/TECH_EVALUATION.md`）逐项对照。
> 结论速览：**不建议按此方案重构**。若最终确定要换，**Tauri 是比 Electron 更优的形态**；
> 而无论换什么，**都不该换掉 Python 协议层**。

---

## 0. 一句话结论

| 命题 | 判断 | 依据 |
|---|---|---|
| Rust 做协议底层 | ❌ **亏本** | 协议层不是瓶颈（余量 600×），Rust 换不来收益，却引入工具链/调试/迭代成本 |
| Electron 做 UI | ⚠️ **过度** | 体积 733MB（本机实测）、内存 150MB+，为"单机小工具"付出桌面级开销 |
| （对照）Tauri 做 UI | ✅ **若必须换，选它** | 复用系统 WebView2（本机已装），体积可 <10MB |
| （对照）PyQt 壳 + 内嵌 Web | ✅✅ **最优** | 零重写、保留现有协议层、渐进获得 Web 生态 |

**核心判断**：这个方案把成本花在了**不痛的地方**（协议层性能），
却留下**真正的痛点**未解（持久化、静态数据、API）——
它是一次"技术栈升级"，不是"产品问题解决"。

---

## 1. Rust 做协议层：为什么是亏本买卖

### 1.1 收益侧：性能提升无处释放

实测（`TECH_EVALUATION.md` §1）：Python 全管线 **42,002 帧/s**，
游戏实际负载 **5~50 条/s**，**余量 600 倍以上**。

Rust 能把 23.8µs/帧 降到约 1µs/帧（估计）——
但这是在"每秒处理 5 万条消息"才有意义的优化。
**游戏永远打不到这个量级。** 优化一个没有负载的环节，收益恒等于零。

### 1.2 成本侧：1200 行要重写，且是最难的部分

| 要重写的模块 | 行数 | 难度 |
|---|---|---|
| `protocol/frames.py` 切帧 | 118 | 中（假 magic 同步、粘包） |
| `protocol/crypto.py` 双变体解密 | 69 | 低 |
| `protocol/records.py` s2c/c2s 拆分 + trailer | 145 | **高**（两套结构头+短头，全是实测反推） |
| `protocol/wire.py` protobuf 字段号树 | 146 | 中（嵌套从严判定+容错） |
| `protocol/schema.py` schema 双路解码 | 109 | 中（跨 JSON 定义递归） |
| `protocol/opcodes.py` 目录 | 66 | 低 |
| `capture/reassembly.py` TCP 重组 | 152 | **高**（乱序/重传/全零段回滚，踩过坑） |
| `capture/npcap_source.py` 接入 | 217 | 中（队列+线程模型） |
| **合计** | **~1022 行 + 测试 785 行** | |

这些代码不是"翻译一遍"就行的——**它们的每一行都对应一次抓包实测的坑**
（全零探测段导致整批下行丢失、假 magic 同步、s2c/c2s 三种结构头……）。
重写等于把这些坑重新踩一遍，且现有的 **110 项测试**（含 785 行协议测试）
锁定的行为要全部重新验证。

### 1.3 Rust 在本项目的额外硬伤

1. **工具链本机都没装**（`cargo`/`rustc` 均无）。而且这不只是"装一下"——
   目标用户是**普通玩家**，与他们无关；但对**你**（唯一开发者）意味着：
   每次改协议（游戏版本更新必然要改）都要等编译，调试用 `dbg!`/gdb，
   迭代速度比 Python REPL 慢一个数量级。
2. **协议是逆向出来的，且会持续变**。这个项目的核心活动是
   **"抓包 → 猜格式 → 试 → 验证"**。Python 在这个循环里是无敌的
   （改一行，重启即生效；甚至能直接 REPL 里喂字节试解码）。
   Rust 的编译-链接循环会把这个循环拖慢 5~10 倍。
   **这是本项目最关键的敏捷性，比吞吐重要得多。**
3. **schema 递归解码要重新实现**：当前 schema 是外挂 JSON
   （3458 条消息定义、715KB），Python 用 dict 递归天然契合；
   Rust 要处理 `serde_json::Value` 递归或自己做 arena，复杂度不降反升。
4. Npcap 依赖：好消息是 Rust `pcap` crate 在 Windows 上**不需要 SDK**
   （已核实：运行时动态解析入口点，只需装 Npcap 驱动）。
   所以这**不是**阻碍——阻碍在 §1.2/§1.3.1-3。

### 1.4 什么情况下 Rust 才值得

- 要把抓包做成**独立常驻服务**且要处理**生产级流量**（如软路由上跑，Gbps 级）；
- 要支持**多路高并发抓包**（同时监听多个账号/多台设备）；
- 要做**实时高频回放压测**（如 100 倍速重放验证策略）。
这些都不是当前需求。**预留**：架构上已经留好了——
`CaptureSource` 协议 + `protocol/` 纯函数无 IO，将来真需要时
可以用 Rust 写一个独立进程，通过本地 socket 喂字节给 Python 管线。
**这样只重写需要性能的部分，而不是全部。**

## 2. Electron 做 UI：代价与替代

### 2.1 实测体积对照（本机）

| 形态 | 体积 | 说明 |
|---|---|---|
| **Electron 应用（实测：ZCode 自身）** | **733 MB** | 含完整 Chromium + Node |
| 当前 PyQt6 venv | 248 MB | 其中 PyQt6 214MB（含 Qt 全量） |
| roco_helper 发行版 | 15.6 MB | Qt+UPX 加壳的结果 |
| **WebView2 运行时（Tauri 依赖）** | **系统已有**（本机 154.x） | Windows 10/11 预装 |
| Tauri 应用（官方宣称） | **< 10 MB** | 复用系统 WebView2，不带 Chromium |

对"给玩家用的单机小工具"，733MB 是**不可接受**的（对比竞品 15.6MB）。
玩家下载一个 700MB 的宠物查询器，第一反应是"这什么鬼"。

### 2.2 Electron 的额外问题

1. **内存**：空载 ~150MB，加载大表格后更高（每进程独立 V8 堆）。
   对比 PyQt 当前无感。
2. **安全面**：Electron 需要维护 `nodeIntegration`/`contextIsolation`/CSP；
   本项目虽只监听本地，但 UI 若渲染抓包内容（含游戏文本），
   XSS→RCE 风险需要认真处理。
3. **打包签名**：Windows 上未签名的 Electron 应用会被 SmartScreen 拦（"未知发布者"），
   Python 打包同样有此问题——**两者都要解决**，不是 Electron 独有。
4. **它没解决任何现有痛点**：换 Electron 后，持久化/静态数据/API 依旧从零写。

### 2.3 若最终确定换：选 Tauri 不选 Electron

| | Electron | **Tauri** |
|---|---|---|
| 内核 | 自带 Chromium | 系统 WebView2（本机已装） |
| 体积 | 733MB（实测） | <10MB |
| 后端 | Node.js | **Rust**（正好能吃下协议层） |
| 内存 | 150MB+ | 依赖系统 WebView（~50MB） |
| 抓包 | 需 node 绑定或用 Rust sidecar | Rust 原生，Npcap 无 SDK 依赖 |
| 组合 | 「Rust 协议 + Electron UI」= 两套运行时 | 「Rust 协议 + Web UI」= **一套** |

**关键点**：用户提的"Rust 做协议 + Electron 做 UI"其实是**两个运行时并存**
（Electron 的 Node + Rust 二进制），通信还要过 IPC。
**Tauri 恰好把这两者合并成一个**——Rust 既是后端也是协议层，前端复用系统 WebView。
如果真要走"Rust + Web UI"这条路，**Tauri 是这个想法的正确形态**。

**但 Tauri 依然要重写协议层**（§1.2 的 1022 行 + 785 行测试），
所以 §1 的所有成本结论**对它同样成立**。

## 3. 决策矩阵

| 方案 | 重写量 | 体积 | 迭代速度 | 拿到 Web 生态 | 解决现存痛点 |
|---|---|---|---|---|---|
| **A. 现状（PyQt）** | 0 | 248MB venv | ⚡ 最快 | ❌ | ❌ |
| **B. PyQt 壳 + 内嵌 Web（推荐）** | 增量（加 FastAPI） | 248MB + 0 | ⚡ 快 | ✅ 渐进 | ✅ 可承载 |
| C. Tauri + Rust 协议 | ~1022 行 + 785 测试 | <10MB ✅ | 🐢 慢 | ✅ | ❌ 需另做 |
| D. Electron + Rust 协议（本题） | ~1022 行 + Node 层 | 733MB ❌ | 🐢 最慢 | ✅ | ❌ 需另做 |

> ⚠️ **承载形态修正（2026-10-10）**：本文与 `TECH_EVALUATION.md` §4.2 曾建议用
> `QWebEngineView` 承载 Web 页面——**不要这么做**。实测 `PyQt6-WebEngine-Qt6`
> win_amd64 wheel = **132.4 MB**（自带完整 Chromium，量级向 Electron 靠拢）。
> 改用 **pywebview + 系统 WebView2**（本机已装，额外体积 ≈ 0）。
> 详见 `docs/ARCHITECTURE_DECISION.md` §3。
>
> 另：本文 §1.2 提到的"现有 110 项测试"已过期——当前为 **175 项**（2026-10-10 实测）。
>
> 表格中 B 行的"体积 248MB + 0"也需按此理解：**仅当承载形态用 pywebview 时才成立**。

**排序：B ≫ C > A > D**

- **B 胜在**：零重写、保留踩过坑的协议层、立即获得 Web 生态、可渐进不冒险。
- **C 唯一优势是体积**（对下载体验有价值），但要付全部重写成本 +
  牺牲协议迭代速度——**留作 V3 之后的"发行形态优化"再评估**，
  那时协议稳定了、功能齐了，重写的风险才可控。
- **D 最差**：C 的全部成本 + Electron 的全部代价，且两套运行时。

## 4. 如果确实想换技术栈，正确的时机与路径

**时机**：等协议层稳定（各业务域实测完、版本更新不再频繁改解析）、
功能齐备（16 模块有了骨架）之后。**现在换 = 用最贵的代价买最不需要的东西。**

**路径（渐进式，永远保持可运行）**：

```
第 1 步（现在该做的，与换栈无关）
  SQLite 持久化 + 静态数据导入 + FastAPI 对外 API
  → 这三件事让数据有资产价值；Rust/Tauri 都不解决它们

第 2 步（UI 渐进 Web 化）
  宠物页 → Web（pywebview + 系统 WebView2）
  → 验证 Web UI 的收益是否真实（筛选器/矩阵/图表）

第 3 步（可选，协议稳定后）
  若体积成为真实痛点（用户抱怨下载大）：
  用 Rust 重写 protocol/ + capture/ 为独立进程，Tauri 承载 UI
  → 此时 Python 版作为"参考实现"和测试对照，风险可控
  → 或者更轻：给 Python 打包（PyInstaller），
     体积约 40~60MB 且无需换语言
```

**一句话**：现在最该做的是**把数据变资产**（持久化/静态数据/API），
而不是把技术栈变时髦。等这些做完，你会有更多信息判断值不值得换。
